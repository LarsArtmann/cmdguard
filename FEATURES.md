# cmdguard Features

> Honest inventory of what this project does, by status. Generated by studying
> the actual code — not the marketing claims. Every status is backed by
> `file:line` evidence. Updated as features ship, change, or break.

---

## Status legend

| Status                    | Meaning                                                                                |
| ------------------------- | -------------------------------------------------------------------------------------- |
| 🟢 `FULLY_FUNCTIONAL`     | Works as intended; code present **and** confirmed working (tests pass).                |
| 🟡 `PARTIALLY_FUNCTIONAL` | Ships but has known gaps, zero test coverage, or edge-case issues.                     |
| 🔴 `BROKEN`               | Code exists but does not work / is disabled / fails.                                   |
| ⚪ `PLANNED`              | Designed or documented but **no code exists yet**.                                     |
| 📦 `SUB-MODULE`           | Lives in an optional importable sub-module (`github.com/larsartmann/cmdguard/<name>`). |

> A feature earns `FULLY_FUNCTIONAL` only when you can point to the code that
> delivers it AND confirm it works. If you're unsure, it's `PARTIALLY_FUNCTIONAL`
> at best — never round up.

## Architecture Notes

### TypeHandler Registry

```
TypeHandler interface {
    Register(flags, tag) error       // Add flag to pflag.FlagSet
    Parse(value, tag) (any, error)   // Parse string → Go value
    Default(tag) any                 // Compute default value
}
```

All type dispatch (primitives + 9 custom types) flows through a single registry
with copy-on-write semantics. Custom types added via `RegisterTypeHandler()`.

### Copy-on-Write Registries

`FlagRegistry` shares global `typeRegistry`/`validatorRegistry` lazily via `share()`
and clones only on first write via `register()`. Package-level writes go to global
defaults; instance-level writes trigger COW clone. Reduces `NewCLI` by ~48%.
