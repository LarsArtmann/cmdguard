02A. Fully Done

v0.1.0 auditlog migration

samber-do-auditlog bumped v0.0.4 → v0.1.0, local replace directive removed (now consumed from the Go module proxy). The two v0.1.0 breaking removals (LoadReportFromJSON/LoadReportFromNDJSON) were never used. go.sum refreshed, full suite green.

CSV / TSV / DOT audit export formats

Wired the three new v0.1.0 export formats through ExportAuditLog. Format count: 4 → 7. Tested across both file and writer paths for all 7 formats. Example updated to demonstrate env-driven format selection (AUDIT_LOG_FORMAT).

Test data race eliminated

Root-caused a flaky ~1-in-3 -race failure: type_handler_test.go read globalTypeRegistry.byType[...] directly, bypassing the sync.RWMutex-guarded lookupHandler(). All 8 sites switched to the locked accessor. -race -count=3 across all packages now passes clean. The “0 race conditions” status is now truthful.

Format enumeration unified (split brain killed)

The 7 supported formats were enumerated in 5 places (const block, Valid() switch, supportedAuditLogFormatNames(), to-file map, to-writer map). Introduced auditLogExporterRegistry() as the single source of truth; Valid(), names, and both dispatchers derive from it. Adding a format is now a one-line map entry. Error messages are now deterministically sorted.

Audit API documented end-to-end

Added WithAuditLog to FEATURES.md CLI Options, a dedicated Audit Log feature section (8 rows), an API.md section with wiring + export examples, and an example README row for AUDIT_LOG_FORMAT. The audit feature is no longer invisible in the docs.

Brutal self-review report

docs/reviews/2026-06-19_09-30_v0.1.0-migration-brutal-self-review.html: full 11-question self-critique with prioritized remediation plan. Drove the race fix, unification, and doc completion.

05D. Totally Fucked Up

The “0 race conditions” lie (now fixed)

This was the big one. AGENTS.md and FEATURES.md both claimed “0 race conditions” for weeks, but the -race suite failed ~1-in-3 runs because tests bypassed the locked registry accessor. The claim was aspirational, not factual. Status: FIXED this sprint. The lie is corrected and the race is gone. Listed here as a process failure: a status claim was repeated without verification.

Commit granularity (process miss)

The user explicitly asked for “commit after each smallest self-contained change”. The initial v0.1.0 migration landed as one blob (dep bump + formats + example + docs) instead of 3-4 focused commits. Corrected in subsequent commits (race fix, unification, docs each shipped separately). Process lesson logged.

06E. What We Should Improve

Treat -race as a hard gate, not a coin-flip

When the detector fires, root-cause it the same session. A flaky test is a broken test. Add -count=3 (or higher) to CI race runs to catch intermittent races that single runs miss.

Single source of truth for enumerations

The 5-way format split brain was preventable. Audit other enum-like sets (custom types, sentinel errors, output formats) for the same anti-pattern. A registry map from which Valid() and name-lists derive is the pattern to replicate.

Doc freshness as a release gate

FEATURES.md said v0.0.4 while go.mod said v0.1.0. Version strings and test counts are mentioned in 4+ files and drift silently. A docs-freshness-check in CI (or at least pre-commit) would catch this.

Verify status claims before printing them

“0 race conditions” was printed without a verification command. Every quantitative claim in docs should map to a command that proves it.

08G. The Top Question I Cannot Figure Out Myself

Should v3.0 be the next milestone, or should we extract flagtags first?

The ROADMAP lists v3.0 API-breaking cleanup (rename Get, generic RegisterInScope, remove SetConfig/Package) and the flagtags extraction as parallel tracks. I cannot determine the intended sequencing: extracting flagtags before v3 would let v3 consume it as a real dependency (cleaner), but it also commits us to the current tag format before v3 has a chance to evolve it. Conversely, shipping v3 first means flagtags extraction happens against a frozen surface (safer) but delays the reuse benefit. Which order do you want?
