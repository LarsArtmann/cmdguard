WithCleanup[T] — post-RunE cleanup that fires on error

pkg/cmdguard/v2/cli_options.go:171 · cli.go:281 applyCleanupHooks · cli_cleanup_test.go · commit 72059b2

Wraps every command's RunE once at Execute time via a tree-walk, so it covers both cmdguard-managed Command[T,F] and raw cobra subcommands (the escape hatch). Hook signature func(cmd, cfg, runErr) error; original runErr never swallowed (cleanup errors joined via errors.Join). Idempotent (cleanupWired guard) — calling Execute twice does not double-wrap. No-op when no hooks registered. 8 tests: success, error, ordering, config passthrough, cleanup-error-on-success, runErr-not-swallowed, double-Execute idempotency, no-hooks no-op.

BuildFlow: escape hatch is the PRIMARY pattern, not the edge case

BuildFlow internal/cli · 27 raw cobra RunE handlers, ZERO Command[T,F] usages

The "gradual migration from plain Cobra" comment in root.go is still aspirational. BuildFlow registers every subcommand as a raw *cobra.Command and uses the escape-hatch APIs (ConfigFromContext, WithPostFlagParse) exclusively. cmdguard's first-class Command[T,F] / AddCommand API is exercised only in examples/taskctl, not in the real consumer. This is not broken, but it means the primary API surface is validated by an example, while the escape hatch is validated by production.

eWhat We Should Improve

Close the WithClosure consumer loop

Every other v2.10.0 API was reverse-engineered from BuildFlow. WithCleanup was built from theory. Migrating BuildFlow's diCtx.Close() into a WithCleanup hook would make it the seventh consumer-proven API and close the consistency gap.

Decide the escape-hatch vs Command[T,F] question

BuildFlow lives entirely in the escape hatch. Either commit to it as a first-class supported pattern (more docs, more tests around raw cobra), or start migrating BuildFlow handlers to Command[T,F]. The current ambiguity is the single biggest strategic decision.

Fix the infertypeargs noise

A mechanical gopls fix-up pass removes ~260 redundant type arguments. Low effort, high signal-to-noise win. examples/taskctl alone has 10+ sites.

Coverage gap analysis

86.7% is fine but unexamined. A go test -coverprofile + per-file review would show whether the uncovered 13.3% is trivial error formatting or a real untested code path.

Standardize status-report format

This session produced 3 Markdown status reports; the skill mandates HTML (this report). Pick one — HTML is correct for snapshot reports, Markdown for living docs. The split-brain should end here.

Make the consumer-prove discipline a release gate

The "prove every new API in BuildFlow before release" rule worked — it caught nothing broken but de-risked everything. Codify it: no new public API ships without a BuildFlow (or example) call site in the same release.

gTop Question I Cannot Answer Myself

The strategic fork

Is the "raw cobra escape hatch" BuildFlow's intended permanent pattern — or a transitional state that should migrate to Command[T,F]?

Why I can't resolve this: it's a product-direction question, not a technical one. The evidence cuts both ways:

  • For "permanent": BuildFlow has zero Command[T,F] usages across 27 handlers. It migrated to every escape-hatch API (ConfigFromContext, WithPostFlagParse, hidden:"true") cleanly and shipped faster for it. Real consumers with large existing cobra apps cannot rewrite every handler — the escape hatch may BE the product.
  • For "transitional": the code comment says "gradual migration." Command[T,F] is the type-safe, footgun-free API the library exists to provide. If the primary consumer never uses it, the flagship example is the only proof it works in anger, and v3.0 API cleanups (P2 #30–33) optimize a surface no consumer exercises.

Why it matters: the answer decides whether the next sprint invests in (A) hardening the escape hatch as first-class — more docs, BDD tests, a migration guide — or (B) migrating BuildFlow handlers to Command[T,F] and treating the escape hatch as legacy. These are opposite work streams. Every item #1–#11 above leans one way or the other depending on this answer.
