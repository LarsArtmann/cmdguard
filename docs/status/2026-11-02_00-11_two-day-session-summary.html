00Summary

The session started with “what is the end goal?” and ended with the first real down payment on it. The end goal is now written at the top of README.md and AGENTS.md: make it impossible to not create superb CLI apps, with near-zero bugs and minimum code for developers and agents. A full v5 plan (“Paved Road”) maps that goal to four testable properties and eight workstreams.

Two slices shipped additively: a machine-readable describe contract, atomic AddCommands, actionable error hints, the lint baseline rules CG007/CG008, then production batteries (WithBatteries/NewApp) and a human Hint: line. Coverage rose to 90.4%, and the full gate passed twice.

While exercising the hint path, a real bug surfaced: the required, values, and validate tags were parsed and documented but never enforced. ValidateFlags had tests and no production caller. That is now fixed, with env/default awareness, string bounds, meta-command exemptions, and much cleaner error text.

The one decision before tagging anything The validation fix changes runtime behavior and error text. It is correct, but it is a breaking change for a v4 minor. It needs an explicit release vehicle (v4.x with a migration note, an opt-in, or v5) before a release.

02What shipped

W1 · DONE

Machine-readable CLI contract

Describe() / WriteDescription() emit a versioned JSON schema (schema_version: "1") of the whole command tree. A hidden describe command is registered at Execute time; a consumer command of the same name wins, and WithoutDescribeCommand() opts out. Flag metadata pflag cannot model (env, required, values, count, prompt, validate) is attached to cobra annotations at wiring time.

Atomic batch registration

AddCommands[T](cli, cmds...) validates and converts every command before attaching any, accepts heterogeneous flags types through the sealed AddableCommand[T], rejects nil entries, and keys duplicate detection on the cobra name. 03The validation bug

Critical · Latent since the tags were introduced

The tags were parsed, documented, tested in isolation, and never run

pkg/cmdguard/v4/flags.go · ValidateFlags had zero production callers

Live-testing hints exposed it: taskctl add --title ab created a task instead of rejecting the two-character title, and taskctl done reached the handler with id=0 instead of failing on the missing required flag. 

// Before: dead code (tests only)
func (r *FlagRegistry) ValidateFlags(cmd *cobra.Command) error { ... }

// After: enforced in cli.go (root) and cli_command.go (commands)
if !skipsFlagValidation(c.Name()) {
    if err := registry.ValidateFlags(c); err != nil {
        return err
    }
}

Fixing it surfaced three more issues, all fixed: validation used only flag.Changed (so env/default values escaped), string fields ran the numeric min/max (producing “value is not a number”), and required root flags would have blocked describe/version/doctor.

Impact: behavior change, not just a bug fix Invocations that used to succeed may now fail, and error text changed. Correctness is not in question; release discipline is. This needs an explicit v4.x-with-note, opt-in, or v5 decision before a tag.

06Screw-ups (honest)

Highest risk

Behavior-breaking fix in a v4 minor

Enforcing the tags was correct, but it changes runtime behavior and error text without a release decision or migration note. This is the one thing to resolve before tagging.

Important

No fang-on tests for hints or batteries

Unit coverage uses WithFang(false). The fang path was verified only by live taskctl runs, and taskctl does not use batteries.

Important

go.sum changes were not reviewed

I diffed go.mod after tidy but not go.sum; the final tree gained /go.mod hash lines in several modules. They are benign but unexamined.

Unowned changes

Unexpected working-tree edits were auto-committed

.golangci.yml lost lll and set unlimited max-issues; flake.lock and website dependencies were bumped. I did not author or review them, and now they are in HEAD.

Nice to know

Two self-inflicted breaks during work

I replaced CG006’s rule definition while adding CG007/CG008, and I broke taskctl’s function braces while converting it. Both were caught by tests or the compiler, but verification was reactive.

Nice to know

Schema emitted boolean noise

The first describe schema used omitempty on bools, so every flag reported "required": false. json/v2 keeps false with omitempty; fixed with omitzero after seeing live output.

Housekeeping

Generated artifact churn

Live runs rewrote the tracked taskctl-audit.html; restored at the end of the session.

Process

Batteries shipped before the defaults decision

WithBatteries front-runs the owner’s defaults decision. It is opt-in and reversible, but the order should have been decision first.

Process

Error text compatibility was not considered

Removing the nested prefixes improves UX but can break consumer tests or scripts that match the old text. No shim or compatibility note exists.

07What we should improve

Process

Decide semver before behavior changes. Run the canonical gate after every slice, not after a batch. Diff go.sum as well as go.mod. Keep a checklist that includes the enabled configuration (fang on/off, batteries on/off, strict/draconian).

Design

One source of truth for validation messages. Stable machine error codes. Track config sources so required can be satisfied by a config file. Validate defaults at registration. Resolve parsed types before numeric bounds.

Testing

Golden snapshots for describe/help/error/exit codes. End-to-end env required tests. Fang-on tests. Consumer builds and tests, not just linter scans. Benchmarks for the new hot paths.

Docs

Generate ERROR_REFERENCE from code. Bring QUICKSTART, TUTORIAL, and the website to parity with README and the skill. Record shipped workstreams in ROADMAP, not just the plan.

09Three questions

1. Module path

Move to github.com/larsartmann/cmdguard/v5 (true semantic import versioning, every import changes), or keep /v4 and treat v5 as a deliberate exception? This blocks every rename.

2. Release vehicle

Is the validation enforcement acceptable in a v4.x release with a migration note, must it be opt-in, or must it wait for v5? This blocks tagging.

3. v5 defaults

Should strict validation, signals, and graceful shutdown become the defaults, and should batteries become the default behavior? This decides whether W2/W5 is a flip or a permanent opt-in.
