## e) WHAT WE SHOULD IMPROVE

### Architecture & Type Models

1. **FlagTag is a god struct** — It has 12 fields mixing concerns: parsing metadata (Name, Short, Default, Type), validation (Validate, Required, Values), UI (Help, Prompt), and infrastructure (Env, Count, Field). Consider splitting into `FlagMeta` (identity) + `FlagValidation` + `FlagUI`.

2. **Error types lack structured classification** — We have 60+ sentinels but no error classification (transient vs permanent, user-error vs system-error). The `go-error-family` library (already flagged by go-structure-linter) would give us `Rejection` (user error, 4xx) vs `Transient` (retryable, 5xx) classification.

3. **TypeHandlerFunc is a bag of closures** — The `RegisterFunc`/`ParseFunc`/`DefaultFunc` pattern works but has no compile-time safety. A typed interface per category would catch more errors.

4. **No validator composition** — The `validate:"email,min=5"` string is parsed at runtime. A `Validator[T]` func type with composition (`.And()`, `.Or()`) would be more Go-idiomatic and type-safe.

5. **BranchingFlowContext values are `any`** — `SetValue(key, value any)` loses type information. Generic typed keys (`type Key[T any] struct{ name string }`) would prevent runtime type mismatches.

## g) My #1 Question I Cannot Figure Out Myself

**The `os.Setenv("NO_COLOR", "1")` in `Execute()` at `cli.go:185` (50% coverage):**

The current code sets `NO_COLOR=1` process-wide so that fang/lipgloss picks it up. This is a real bug — it mutates global state, breaks concurrent tests, and is not goroutine-safe.

However, fang's styling system reads from the environment via `colorprofile`. The fix path depends on:

1. **Does fang v2 support programmatic color disable?** I.e., can we pass an option to fang's `PrintHelp` that forces no-color without env mutation?
2. **If not**, should we document this as a known limitation and add `//nolint` + a defensive mutex, or should we fork/PR fang to support programmatic color control?
3. **Alternative:** Use lipgloss's `SetColorProfile` directly on the renderer, bypassing the env var entirely. But this requires understanding fang's internal renderer construction.

This requires reading fang's source code or testing its API to determine the right fix. I cannot resolve this without either (a) checking fang's API surface, or (b) your input on the desired approach.
