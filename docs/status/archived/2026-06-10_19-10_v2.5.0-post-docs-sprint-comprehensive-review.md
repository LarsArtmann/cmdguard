## g) My #1 Question I Cannot Figure Out Myself

**The `os.Setenv("NO_COLOR", "1")` in `Execute()` at `cli.go:185` (50% coverage):**

The current code sets `NO_COLOR=1` process-wide so that fang/lipgloss picks it up. This is a real bug — it mutates global state, breaks concurrent tests, and is not goroutine-safe.

However, fang's styling system reads from the environment via `colorprofile`. The fix path depends on:

1. **Does fang v2 support programmatic color disable?** I.e., can we pass an option to fang's `PrintHelp` that forces no-color without env mutation? **→ answered above — fang reads colors via the environment; the env-var path stays (AGENTS.md)**
2. **If not**, should we document this as a known limitation and add `//nolint` + a defensive mutex, or should we fork/PR fang to support programmatic color control? **→ answered above — documented as a deliberate trade-off, no fork needed**
3. **Alternative:** Use lipgloss's `SetColorProfile` directly on the renderer, bypassing the env var entirely. But this requires understanding fang's internal renderer construction. **→ answered above — not pursued; the documented env-var approach won**

This requires reading fang's source code or testing its API to determine the right fix. I cannot resolve this without either (a) checking fang's API surface, or (b) your input on the desired approach.

**Answered:** kept by design — `--no-color` sets `NO_COLOR=1` for fang, and the behavior is documented in AGENTS.md. Fang reads colors via `colorprofile` from the environment, so the env var remains the integration path; the mutation is a deliberate, documented trade-off.
