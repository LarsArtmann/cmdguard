cmdguard: What 18 Fleet Reviews Say We Must Improve

Every consumer project wrote a point-in-time review of cmdguard (docs/review/libs/cmdguard.md). This report reads all 18 and distills them into concrete fixes for the documentation, the positioning, and the consumer-facing AI skill — so the next adoption decision takes hours, not days.

00Summary

The library itself is winning: adopters leverage it hard (io-surface scored 100/100, CV kept every v5 battery), the migration codemod and batteries-on defaults landed well, and twelve non-adoptions are mostly correct rejections with recorded flip triggers. The gap is not the product — it is that nearly every review had to verify the same handful of facts from source because the docs, the README positioning, and the AI skill do not carry them.

The bottom line Three facts block or slow almost every review: (1) the dependency weight (80 net-new modules measured) has no documented answer; (2) the composition story (fang interop, go-error-family exit codes) is undocumented work reviewers redo per project; (3) the godoc understates the tag set — doc.go omits 6 of 13 tags. Fix those three, then harvest the reviews' source-verified facts into the AI skill.

+

01Docs findings

Ordered by impact. Every finding cites the project(s) that hit it.

Critical · Blocks adoption & re-measured per review

D1 — The dependency-weight story has no documented answer

graph-features-language · business-networking · Cyberdom · go-taskqueue · dnsblockd

GFL measured 80 net-new modules (36% graph growth) into a 220-module graph — identical with every lean switch on, because "the lean options are runtime switches, not import-graph prunes: the root module unconditionally imports charm.land/fang/v2 (cli.go:14)". business-networking counted 64 indirect requires against its zero-dep identity. Cyberdom and go-taskqueue list dep cost as a blocker. Every review re-measured this from scratch; none found the numbers in our docs.

Fix Publish a measured "cost of adoption" page: module-graph delta for default vs slim profiles, why WithFang(false) does not prune imports today, and the tracked plan for a slim root profile (upstream proposal cmdguard#25). Keep the numbers in the AI skill so reviewers stop re-measuring.
Critical · Wrong first impression in godoc

D2 — doc.go understates the tag set

pkg/cmdguard/v5/doc.go:65 · found by google-domain-detector

The package doc omits values, validate, local, hidden, prompt, and secret — 6 of the 13 tags the runtime actually enforces. The review's words: "cmdguard's own docs understate its tag set — library-side doc gap, not consumer misuse." A consumer skimming godoc concludes the validation layer is half the size it is.

Fix Sync doc.go to the 13-tag table and add a drift guard (same pattern as scripts/check-guide-sync.sh or the docgen drift test) that fails when a parsed tag name is missing from the package doc.
Important · Undocumented composition work, redone everywhere

D3 — No composition guides: fang and go-error-family

browser-history · Cyberdom · invoices · CV · Code-To-CV-Agent · journal

The single most repeated blocker: "who owns error printing and exit codes?" browser-history and Cyberdom both wrote "wiring them together is undocumented work". Meanwhile the facts that dissolve the conflict exist only in source: dispatch goes through fang.Execute (cli.go:670-674) with WithFangOptions/WithFangErrorHandler so adoption keeps an existing fang UX; ExitCode(err) honors a chained ExitCoder treating 0 as "no override" — byte-for-byte the go-error-family convention.

Fix One guide: "cmdguard alongside fang and go-error-family" — the print-once contract, the 0-as-no-override semantics, the decision table (framework prints vs your classifier prints), and a worked example of mounting cmdguard under an existing HandleError boundary.
Important · The fleet's actual adoption path is buried

D4 — Incremental adoption is a README section, not a guide

journal (M8 pilot) · invoices (trial plan) · graph-features-language (executed blueprint)

Three projects independently discovered the same migration pattern from source: cmdguard commands expose their underlying cobra command, so a typed command mounts under an existing raw root "surface byte-identical" (journal's pilot, 2026-11-08). Invoices designed a half-day trial around it; GFL's blueprint executed as written. This is the strongest adoption promise we have — "one command at a time, no big-bang rewrite" — and it deserves a first-class guide with the mount recipe.

Fix A guide titled "Adopt one command at a time": the mount recipe (typed command → its cobra command → existing root's AddCommand), journal M8 as the worked example, and the success criteria invoices drafted (delete-a-tag → flag disappears, env tag overrides, help unchanged, exit codes asserted).
Important · Mental-model surprise

D5 — Positional args are not flag fields; say it early

graph-features-language (needed source anchors to write its migration)

GFL's migration had to verify from source that positionals are read via cmdguard.ArgsFromContext(ctx) with WithExactArgs(n) as the arity guard — they are not fields of the flags struct. This belongs in the QUICKSTART flags section, not in a reviewer's grep history.

Important · Undocumented limits cause rejections

D6 — Document what the config layer does NOT do

dnsblockd · audiblesync · business-networking

dnsblockd rejected adoption partly because it had to discover from source that "v5's config layer is still a file-only KoanfLoader plus flat per-flag env tags" — no hierarchical PREFIX__NESTED__KEY env provider, no external loader returning raw bytes. Those are real limits; consumers with deployed hierarchical env contracts will reject on them. Stating the limits (and the extension-hook roadmap) in the config docs converts a discovered rejection into a documented boundary.

Nice to have · Missing recipes

D7 — Four capabilities lack "how to actually use this" recipes

cv / CV · google-domain-detector · Code-To-CV-Agent

Consumers leave value on the table because the recipe is not written: (a) describe is emitted everywhere but no docs show how to consume the JSON (agent tooling is the named consumer in three reviews); (b) WithDoctorCheck — google-domain-detector runs a doctor with "zero real checks" on a network tool; (c) exit-code differentiation via NewExitError(2, ...) for usage-vs-failure; (d) RecoveryMiddleware — CV noted "a crashed handler today takes the process down ungracefully" before wiring it. Each is an S-effort docs example.

Nice to have · Version + toolchain facts

D8 — Make the Go 1.27 floor and the v4 retirement loud

business-networking · Cyberdom · go-taskqueue

business-networking's hard blocker: "cmdguard's go.mod declares go 1.27; bn literally cannot import it without a toolchain bump." go-taskqueue flagged "v4 had been uninstallable via go get since v4.2.1" as a trust question. QUICKSTART should state the minimum Go version in the first code block, and the version page should carry the clean retirement story: v4 frozen final at v4.3.1 on release/v4, master on v5.

02Marketing findings

The README hook works; what is missing is the honesty layer that converts readers into right-fit adopters.

Important · Prevents wrong-fit adoption

M1 — Publish the "when to adopt" size guide

Cyberdom · Code-To-CV-Agent · audiblesync · pbx-lens · webphone

The reviews independently converge on thresholds: "cmdguard's value shows up at five-plus commands" (Cyberdom), a ~15-subcommand revisit trigger (Code-To-CV-Agent), "two verbs is the threshold where a command table beats argv archaeology" (audiblesync), "a second binary joins the module" (pbx-lens, webphone). Publishing these as an explicit adopt/defer decision table makes correct rejections a success of our positioning rather than evidence of overreach — and arms every future review with the same rubric.

Important · Steering

M2 — State the anti-fit contexts up front

cqrs-htmx · webphone · browser-history · pbx-lens

Four review archetypes should never reach the adopt stage: library repos with no CLI (cqrs-htmx: "a CLI framework in a library repo"), systemd-managed servers whose front is journald not a terminal (webphone: styled help has "no terminal to render to"), owner-maintenance toolsets ("it presumes a CLI that is a product"), and fleets with a recorded no-Cobra policy (pbx-lens). A short "cmdguard is for product CLIs driven by humans or agents in a terminal" boundary statement on README and website saves every one of these reviews a cycle.

Nice to have · Social proof invisible

M3 — Surface the fleet adoption numbers

profileagent census · io-surface · go-credentials-store

The proof exists but is scattered: "40 repos carry a go.mod require" (checkout census, 2026-11-17), io-surface's 100/100 utilization audit, credentials-store as first production v5 consumer (bumped the day v5.1.0 landed). README/website should carry one adopters line with these numbers.

Important · Trust

M4 — Manage the churn narrative with a release policy

go-taskqueue

The harshest marketing line in the corpus: "the 3-day tag cadence + same-day major retirement is churn, not maturity." The facts are on our side — v5.0.0→v5.1.0 was additive-only, +101 non-test lines, verified diffable — but we never say so. Publish a release policy: what belongs in a minor, the additive-only guarantee observed in practice, and the frozen-line policy (v4 at v4.3.1).

Nice to have · Quotable proof unused

M5 — Market with the deletions the reviews measured

business-networking · invoices · graph-features-language

The reviews hand us concrete "what cmdguard deletes" numbers: 97 lines of hand-maintained help whose doc comment lists 7 of 14 commands (business-networking), 69 manual flag registrations plus decorative tags duplicated by hand and a root/solcom --verbose shadow bug (invoices), 7 swallowed flag-read errors and os.Exit inside Run funcs (GFL). A "real code this replaces" section with these measured cases is stronger than any feature list.

Nice to have · Audience segmentation

M6 — Segment fleet vs third-party messaging

graph-features-language (owner directive)

GFL's review records the owner directive: fleet projects use the owner's libraries regardless of the ~15-module gate — but the same review keeps the slim-profile proposal valuable "for third-party consumers." Marketing should say this openly: fleet adoption is the default, the slim profile is the path for external users with tight graphs. It converts the weight objection from a contradiction into a stated policy.

03AI skill findings

The skill (.agents/skills/cmdguard/SKILL.md, fan-out symlinked) is the most-trusted artifact in the corpus — reviews cite it by line number. That trust is exactly why its gaps matter: whatever is missing from it, every AI session re-derives from source.

Critical · Multiplied work across every session

S1 — Harvest the source-verified facts into the skill

findings D1, D3, D4, D5 all resurface here

Six facts were verified from cmdguard source by multiple independent reviews and belong in the skill's gotchas:

  • ExitCode(err) honors ExitCoder with 0 as "no override" (go-error-family compatible; CV deleted its max(·,1) floor on v5's non-nil⇒non-zero guarantee).
  • Dispatch goes through fang.Execute; WithFang(false)/WithFangOptions compose, adoption does not lose an existing fang UX.
  • Typed commands mount under a raw cobra root, surface byte-identical (the incremental path).
  • Positionals come from ArgsFromContext(ctx), never flag-struct fields.
  • Lean switches (WithoutBatteries, WithFang(false)) are runtime-only; the import graph is unchanged (80 net-new modules measured).
  • Describe() before Execute omits the auto-registered commands (registered at Execute time).
Important · Wrong recommendations

S2 — Add a "when NOT to use cmdguard" decision block

pbx-lens · cqrs-htmx · webphone · audiblesync archetypes

The skill should encode M1/M2 so AI assistants stop pushing adoption into library repos, no-terminal server binaries, and sub-threshold CLIs — and instead produce correct rejection rationales with flip triggers, which is what the fleet's best reviews do.

Important · Rot risk

S3 — Guard the skill against source drift

AGENTS.md already warns: "source-line references that can rot"

The skill cites source lines that move; the website already has a truth gate (scripts/check-guide-sync.sh) but the skill has none. Add a check that the skill's tag table, API names, and cited symbols still exist in source — ideally fed by the same fact table docgen uses (D2's guard), so doc.go, the skill, and the website cannot disagree.

Nice to have · Reviewer ergonomics

S4 — Ship standard verification recipes in the skill

every review's "How to verify" section

All 18 reviews end with grep/git verification blocks; they re-invent the same commands each time. A canonical "verify a consumer's usage" recipe in the skill (pin check, symbol census, tag-count greps) makes every future audit cheaper and uniform.

Nice to have · Repeat evaluations

S5 — Encode when cmdguard-lint is worth wiring

CV (evaluated, not wired) · google-domain-detector (free miss)

CV correctly declined the lint submodule (its stale-major target class is empty) while google-domain-detector listed "cmdguard-lint in CI (free)" as a missed item. The skill should carry the decision rule — wire it when a graph spans multiple cmdguard majors or adoption is growing — so consumers stop re-evaluating it per project.
