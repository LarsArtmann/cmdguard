High-Impact Opportunities

The features that would transform cmdguard's DI story from "basic wrapper" to "best-in-class CLI DI experience."

1. Lifecycle Hooks via InjectorOpts
HIGH IMPACT

samber/do v2 provides 6 lifecycle hooks in InjectorOpts that fire at every stage: before/after registration, invocation, and shutdown. cmdguard currently creates its injector via do.New() which uses zero options.

Why it matters: These hooks enable structured logging, metrics, and observability for the entire DI lifecycle — without any middleware. Every service registration, instantiation, and shutdown becomes observable.

InjectorOpts{ HookBeforeRegistration: []func(*Scope, string){ ... }, // validate, log HookAfterRegistration: []func(*Scope, string){ ... }, // metrics HookBeforeInvocation: []func(*Scope, string){ ... }, // tracing start HookAfterInvocation: []func(*Scope, string, error){ ... }, // tracing end HookBeforeShutdown: []func(*Scope, string){ ... }, // log HookAfterShutdown: []func(*Scope, string, error){ ... }, // audit Logf: func(format string, args ...any) { slog.Info(fmt.Sprintf(format, args...)) }, }

How to integrate: Add WithDILogging[T](fn) and WithDIHooks[T](opts) CLI options. Pass hooks to do.NewWithOpts() instead of do.New() in NewScope(). Optionally expose per-hook CLI options like WithDIInvocationHook[T](fn).

📊 Observability
🔍 Debugging
⚡ Zero-cost when unused
🏗️ NewWithOpts instead of New
2. ShutdownOnSignals — Graceful OS Signal Handling
HIGH IMPACT

cmdguard has WithSignalHandling[T]() which sets up a context cancelled on SIGINT/SIGTERM — but it does NOT trigger DI shutdown. The scope's services (implementing ShutdownerWithError) are never notified when the process receives a signal.

samber/do provides injector.ShutdownOnSignals(syscall.SIGTERM, os.Interrupt) which blocks until a signal arrives, then performs dependency-aware parallel shutdown in reverse invocation order. This is a one-liner integration.

// Instead of just cancelling context: injector.ShutdownOnSignals(syscall.SIGTERM, os.Interrupt) // This handles: signal → parallel shutdown → clean exit

How to integrate: Merge with existing WithSignalHandling. When signal handling is enabled, call scope.Injector().RootScope().ShutdownOnSignals() in a goroutine alongside cli.Execute(). On signal, the DI container gracefully shuts down all services, then the cancelled context terminates the active command.

🛡️ Production safety
🔄 Graceful degradation
⚡ Dependency-aware parallel
🔗 Complements existing signal handling
3. Override[T] — First-Class Testing Support
HIGH IMPACT

samber/do's Override[T] and OverrideValue[T] let you replace services in a cloned injector — the standard testing pattern. Combined with injector.Clone(), this enables per-test DI isolation without touching global state.

// In test setup: testScope := scope.Injector().RootScope().Clone() do.Override[*Database](testScope, func(i do.Injector) (*Database, error) { return &MockDatabase{}, nil }) testCLI := v2.NewCLIWithScope("test", "test", Config{}, testScope)

How to integrate: Add Override[T](scope, provider) and OverrideValue[T](scope, value) as cmdguard wrapper functions. Add CloneScope(scope) to clone the DI container for test isolation. Document the testing pattern in examples.

🧪 Testability
🔒 Isolation
📋 Pattern documentation
4. ProvideTransient[T] — Factory Pattern
MEDIUM IMPACT

CLI commands often need fresh instances — request contexts, temporary resources, per-command handlers. ProvideTransient[T] creates a new instance on every Invoke[T] call, acting as a type-safe factory registry.

// Register a factory for per-command contexts v2.ProvideTransient[AppConfig](scope, func(i do.Injector) (AppConfig, error) { return AppConfig{RequestID: uuid.New().String()}, nil }) // Every Invoke gets a fresh instance cfg := v2.Invoke[AppConfig](scope) // unique request ID each time

How to integrate: Add ProvideTransient[T](scope, provider) and ProvideNamedTransient[T](scope, name, provider) wrappers in scope.go.

🏭 Factory pattern
🔀 Per-command isolation
📐 Type-safe
5. Service Aliasing — Accept Interfaces, Return Structs
MEDIUM IMPACT

Go's best practice is "accept interfaces, return structs." samber/do v2 has first-class support: do.As[Concrete, Interface]() for explicit binding, and do.InvokeAs[Interface]() for implicit resolution. This enables proper SOLID DI without coupling consumers to implementations.

// Register concrete implementation v2.Provide(scope, NewPostgresStore) // Bind to interface v2.As[*PostgresStore, TaskRepository](scope) // Consumers only know about the interface repo := v2.Invoke[TaskRepository](scope) // ← interface, not concrete

How to integrate: Add As[Concrete, Interface](scope), InvokeAs[Interface](scope), and AsNamed wrappers. This would make cmdguard the first Go CLI framework with SOLID DI support.

🏗️ SOLID principles
🔌 Decoupling
🎯 Interface-driven design
6. Debug & Introspection API
MEDIUM IMPACT

samber/do provides rich introspection: ExplainInjector() shows the full scope tree and service graph, ExplainService[T]() shows dependencies for a single service, and ListProvidedServices() / ListInvokedServices() enumerate all services.

// cmdguard could add a built-in "di" debug command: // $ myapp di list → shows all registered services // $ myapp di graph → shows dependency graph // $ myapp di explain TaskStore → shows service dependencies // $ myapp di scopes → shows scope tree

How to integrate: Add a DIDebugCommand[T](cli) that exposes subcommands: list, graph, explain <service>, scopes. Wire to ExplainInjector(), ExplainService[T](), ListProvidedServices(), ListInvokedServices().

🔍 Debugging
📊 Visualization
🏗️ Developer experience
7. Individual Service Lifecycle Operations
MEDIUM IMPACT

Currently cmdguard only exposes whole-scope health check and shutdown. samber/do supports per-service operations: do.Shutdown[T](), do.HealthCheck[T](), and their named variants. This enables fine-grained service management.

// Health check a single service err := v2.HealthCheckService[*Database](scope) // Gracefully shutdown a single service err := v2.ShutdownService[*Cache](scope) // Named variants for multi-implementation err := v2.HealthCheckServiceNamed(scope, "cache-redis")
🎯 Fine-grained control
🏥 Targeted health checks
🔄 Selective restart
8. InvokeStruct[T] — Tag-Based Auto-Injection
LOWER IMPACT

do.InvokeStruct[T] auto-injects dependencies into struct fields using do:"service-name" tags. While powerful, it relies on reflection and may not fit cmdguard's explicit, type-safe philosophy. Worth considering for ergonomics but lower priority.

type Handler struct { DB *Database `do:""` // auto-resolve by type Port int `do:"config.port"` // resolve by name } handler := do.InvokeStruct[Handler](injector) // auto-filled
⚡ Ergonomics
⚠️ Reflection-based
🤔 Philosophical question
9. HealthCheck Parallelism & Timeouts
MEDIUM IMPACT

samber/do supports HealthCheckParallelism, HealthCheckGlobalTimeout, and HealthCheckTimeout in InjectorOpts. Currently cmdguard uses do.New() which runs all health checks in parallel with no timeouts.

do.NewWithOpts(&do.InjectorOpts{ HealthCheckParallelism: 5, // max 5 concurrent checks HealthCheckGlobalTimeout: 10 * time.Second, HealthCheckTimeout: 2 * time.Second, })

How to integrate: Add WithHealthCheckTimeout[T](d) and WithHealthCheckParallelism[T](n) CLI options. Switch from do.New() to do.NewWithOpts() in NewScope().

⏱️ Timeout control
🚦 Concurrency limit
🛡️ Production safety

Verdict

cmdguard uses the core DI primitives well — service registration, invocation, scope management, health checks, and shutdown are all solid. The integration quality is high: generic wrappers with nil-safety, error wrapping, and clean abstractions.

The gaps are in observability (lifecycle hooks, logging), production safety (ShutdownOnSignals, health check timeouts), testing (Override, Clone), and advanced patterns (transient, aliasing, introspection).

The biggest ROI comes from Phase 1: switching do.New() → do.NewWithOpts() unlocks 6 lifecycle hooks, custom logging, and health check timeouts with a single-line change. Adding ShutdownOnSignals turns the existing signal handling from "context cancellation" into true graceful shutdown. These are high-impact, low-effort wins that would bring cmdguard to the next level.
