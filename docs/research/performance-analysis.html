📋 Executive Summary

cmdguard is a library for building validated Cobra CLI applications with type-safe dependency injection. Its performance profile is dominated by startup-time overhead (struct-tag reflection, registry cloning, DI wiring) rather than runtime throughput. Since a CLI process runs once and exits, the relevant question is: how much does cmdguard add to the time-to-first-byte of a command?

Bottom Line
For a typical CLI with 5 commands, cmdguard adds under 60 µs of total overhead — less than 6% of Go's own runtime initialization (~1–5 ms). At execution time, cmdguard adds zero overhead beyond raw Cobra/pflag, because flags are parsed by pflag exactly as in vanilla Cobra. The library is production-ready from a performance standpoint.

⚡ CPU Performance

CPU cost in cmdguard splits into two phases: registration (one-time setup at NewCLI / AddCommand time) and execution (per-invocation of a command handler). The registration phase does the heavy lifting; execution is essentially free.

1. Reflection (Registration Only)

Struct-tag parsing via reflect is the single largest CPU cost. It runs once per command at NewFlagRegistry time and never again:

Operation Location Time Allocs Runs
ParseFlagTags (4 fields) config_parsing.go:41 1.9 µs 9 Once per command
NewFlagRegistry (2 fields) flags.go:34 2.2 µs 21 Once per command
setField (reflect.Value) config_setfield.go:16 ~100 ns 0 Per flag per execution
Command.Validate command.go 12 ns 0 Once per command
Good Design: Reflection is Front-Loaded
All reflection (reflect.ValueOf, FieldByName, tag parsing) runs exclusively at registration. At execution time, pflag has already parsed the flags — cmdguard just calls field.Set() via a pre-resolved reflect.Value. This means runtime overhead is dominated by Cobra/pflag, not cmdguard.

2. Regex Compilation (Cached)

The regex validator compiles patterns via regexp.Compile and caches them in a sync.Map (flags_validate.go:260). The first call for a given pattern pays the compile cost; subsequent calls are a map lookup: 

var regexCache sync.Map // map[string]*regexp.Regexp

func validateRegex(value string) error {
    cached, loaded := regexCache.Load(pattern)
    if loaded { re = cached.(*regexp.Regexp) }
    else      { re, _ = regexp.Compile(pattern); regexCache.Store(pattern, re) }
    return ...re.MatchString(val)
}

Good Cached. The cache is unbounded — a theoretical concern if an attacker controls regex patterns, but in practice patterns are finite and developer-defined.

3. Levenshtein Edit Distance (Error Path Only)

SuggestFlag / SuggestCommand compute typo suggestions using a two-row Levenshtein algorithm (flags_suggest.go:44). It allocates two []int slices per call but only runs on the error path (unknown flag/command). Performance is irrelevant here — it never runs for a successful command.

4. Middleware Chain (Per Execution)

buildChain (middleware.go:49) wraps the handler in N closures at execution time. Each closure captures ctx, cfg, info, and prev. For a chain of 3 middleware, this is 3 closure allocations per execution — negligible at ~100 ns each.

5. Type Parsing (Hot Path, But Cheap)

At execution time, each flag value is parsed via the TypeHandler registry. Primitive handlers (strconv.Atoi, strconv.ParseBool, etc.) are zero-allocation:

💾 Memory (RAM)

cmdguard's memory footprint is small and bounded. All allocations happen at registration; the execution path allocates only what Cobra/pflag/DI already allocate.

1. Registry Cloning (Per Command)

Each NewFlagRegistry clones the global typeRegistry and validatorRegistry via maps.Copy. This is the largest per-command memory cost, enabling instance-scoped customization without affecting other commands:

Operation Memory Allocs Detail
NewCLI 8.4 KB 91 Cobra root cmd + DI scope + 2 registry clones
AddCommand 10.3 KB 103 Per command: registry clone + flag registration
NewCommand 288 B 1 Just the Command struct — cheap
NewFlagRegistry (2 fields) 2.8 KB 21 Tag slice + 2 cloned maps
CloneScope 3.2 KB 48 Copies all DI registrations (for testing)
Optimization Opportunity: Copy-on-Write Registries
Every NewFlagRegistry eagerly clones both registries (~2 KB) even when no per-instance customization is ever used. A copy-on-write strategy (share the global map, clone only on first RegisterTypeHandler/RegisterFlagValidator call) would cut ~1.5 KB per command. Impact is minimal for typical CLIs (5–20 commands → 7–30 KB saved) but matters for test suites that create hundreds of CLI instances.

2. Execute (Help Rendering)

The BenchmarkExecute with --help is dominated by fang/lipgloss rendering, not cmdguard itself:

Operation Time Allocs Memory Bottleneck
Execute (--help) 608 µs 9,082 423 KB fang styled output

This is not cmdguard overhead — it's fang's ANSI rendering pipeline. A raw Cobra help output (no fang) would be ~50× cheaper. The 423 KB is freed immediately after rendering since the process exits.

3. BranchingFlowContext

Each Branch call clones the path slice and values map (flow_context.go:106). maps.Clone copies the entire value map on every branch. For deeply nested command trees (rare), this is O(depth × map_size). In practice CLI command trees are 2–3 levels deep, so this is negligible.

4. Defensive Copies

Several methods return defensive copies to prevent callers from mutating internal state:

  • FlagRegistry.Tags() — slices.Clone on every call
  • BranchingFlowContext.Path() — slices.Clone
  • BranchingFlowContext.Children() — slices.Clone
  • FlagRegistry.FlagNames() — allocates new []string

Minor waste These are called infrequently (help generation, suggestions). Acceptable, but an iterator-based API could eliminate these for callers that only need to range over the data.

💿 Disk I/O

Disk I/O in cmdguard is limited to config file loading and the editor integration. Both are blocking, one-shot operations.

1. Config File Loading

WithConfigFile(paths...) tries each path sequentially via os.ReadFile. Missing files are silently skipped (os.IsNotExist). The first existing file wins: 

for _, path := range paths {
    path = expandConfigPath(path)        // os.ExpandEnv + os.UserHomeDir
    data, err := os.ReadFile(path)       // blocking disk read
    if os.IsNotExist(err) { continue }
    return loader.Load(data, cfg)
}

Finding: os.UserHomeDir() Called Per Path

expandConfigPath (config_file.go:78) calls os.UserHomeDir() — a syscall (getenv("HOME")) — on every path that starts with ~/. For a config search with 3 home-relative paths, that's 3 redundant syscalls. The home directory never changes during a process lifetime, so caching it once would eliminate this. Cost: ~1 µs total — negligible, but trivially fixable.

2. JSON Parsing (Double Unmarshal)

The jsonLoader (config_file.go:25) unmarshals the config file twice: once into map[string]json.RawMessage to detect which fields are present, then again into the actual config struct. This doubles the parsing cost for config files but ensures correct flag/env override precedence. Acceptable for one-time startup config.

3. Editor Integration

EditInEditor (editor.go:15) performs full blocking I/O: os.CreateTemp → write content → exec.CommandContext (spawns $EDITOR) → read result → os.Remove. This is inherently slow (seconds — waiting for the user), so library overhead is irrelevant. The temp file is cleaned up via defer os.Remove — safe even on panic.

4. Man Page Generation

manpage.go generates roff/man pages via mango. This is a one-shot generation command, not on any hot path. Output goes to stdout or a file — single write.

🌐 Network

N/A cmdguard makes zero network calls. No HTTP clients, no DNS lookups, no socket connections in the library code.

OpenTelemetry (Opt-In)

TelemetryMiddleware (telemetry.go:24) creates an OTel span per command execution. The span creation itself is in-process (no network). However, if the user configures a real OTel exporter (OTLP/gRPC, Jaeger, Zipkin), spans are flushed over the network at span end (span.End()) or process exit. This is entirely user-controlled — cmdguard never configures an exporter.

Known Limitation: Telemetry Context Propagation
TelemetryMiddleware starts a span but cannot propagate the new context.Context to the handler, because the middleware API signature is next func() error (no context parameter). Child spans created inside the handler will not be linked to the telemetry span. This is a documented design constraint (AGENTS.md gotcha #23), not a bug. Fixing it would require changing the middleware signature — a breaking API change.

URL Parsing

ParseURL (types_url.go:18) uses net/url.Parse which is purely string parsing — no DNS resolution, no connection. The 6 allocations come from URL component struct fields (Scheme, Host, Path, etc.). This is standard library behavior.

🔀 Concurrency & Thread Safety

cmdguard is designed for single-threaded CLI execution but is safe for concurrent registration (e.g., test suites running in parallel). All mutable shared state is protected.

Global Mutable State

Three package-level variables are mutable:

  • globalTypeRegistry — written by RegisterTypeHandler(), read by every NewFlagRegistry
  • globalValidators — written by RegisterValidator(), read by every NewFlagRegistry
  • regexCache — written on first use of each regex pattern

All three are mutex-protected. The AGENTS.md notes that regex validation tests must not run in parallel (gotcha #14) — this is conservative; the sync.Map itself is safe, but test assertions on cache state could race.

Spinner Goroutine

SpinnerMiddleware spawns one goroutine (spinner.go:130) that ticks at 100 ms intervals, rendering braille frames to stderr. The goroutine is cleanly stopped via close(stopCh) protected by sync.Once. If stderr is not a terminal, the spinner is skipped entirely — no goroutine spawned. No goroutine leak risk.

BranchingFlowContext — Explicitly Not Thread-Safe

BranchingFlowContext is documented as not goroutine-safe (flow_context.go:14). This is intentional — CLI command execution is sequential. No locks protect values or children maps. Correct design for the use case.

🚀 Startup Time & Cold Start

For a CLI library, startup time is the only performance metric that matters to end users. A CLI process starts, runs one command, and exits. cmdguard's contribution to this timeline is vanishingly small.

Glamour Rendering (Optional, One-Time)

WithGlamourHelp renders markdown help text at registration time (glamour.go:46), not on each --help invocation. The rendered ANSI is stored in the cobra command's Long/Example fields. This is idempotent (resets the flag after applying) and only runs once. Good design — no repeated markdown parsing.

Binary Size Analysis

The 24 MB example binary includes all charm.land libraries (fang, lipgloss, glamour, huh), OpenTelemetry SDK, go-output with 8 format sub-modules, and Cobra/pflag. This is typical for Go CLI applications with rich terminal rendering. The cmdguard library itself contributes ~7.8 K LOC — a small fraction.

Reducible Users who don't need all 16 output formats can avoid importing the unused go-output/* sub-modules (d2, plantuml, graph, etc.). The output format registries use init() side-effect imports, so each unused format still compiles in. Binary size could be reduced by ~2–4 MB by trimming unused format modules.

🖥️ GPU

Not Applicable cmdguard does not use the GPU. Terminal rendering (fang, lipgloss, glamour) uses ANSI escape codes, which are processed by the terminal emulator — not the GPU directly. The spinner, help output, and markdown rendering are all CPU-to-stdout/stderr text operations.

No OpenGL, Vulkan, CUDA, or any graphics API is used. This is expected for a CLI library.

🔍 Findings & Recommendations

Prioritized by impact × ease of implementation. cmdguard is already fast enough for any CLI use case — these are opportunities for marginal improvement, not critical fixes.

1. Copy-on-Write Registries High Impact Medium Effort

NewFlagRegistry eagerly clones both typeRegistry and validatorRegistry (~1.5 KB, ~12 allocs) per command, even when no per-instance customization is used. Switching to copy-on-write (clone lazily on first register() call) would save ~1.5 KB × N commands. Most CLIs never customize per-instance, so the clone is pure waste. Files: flags.go:40, type_handler.go:99, flags_validate.go:54.

2. Cache os.UserHomeDir() in Config Path Expansion Low Impact Trivial Effort

expandConfigPath (config_file.go:78) calls os.UserHomeDir() on every path with ~/ — a syscall each time. The home directory is immutable during a process lifetime. Cache it in a sync.OnceValue (Go 1.21+). Saves: ~1 µs for multi-path config search. Risk: none.

3. Pre-Build Middleware Chain at Registration Time Low Impact Medium Effort

buildChain (middleware.go:49) allocates N closures per execution. Since middleware is fixed at AddCommand time, the chain could be pre-built once and stored. The closure captures ctx and info which change per execution, so this requires restructuring to pass those as arguments instead of capturing them. Saves: ~3 allocs per execution for a 3-middleware chain. Marginal.

4. Unbounded Regex Cache Low Impact Low Effort

regexCache (flags_validate.go:260) is a sync.Map with no eviction. Patterns are developer-defined (from struct tags), so in practice the set is finite and small. However, if patterns are ever derived from user input, this could grow unbounded. Consider a bounded LRU if user-derived patterns are ever supported. Risk today: none.

5. Defensive Copy Elimination Low Impact Low Effort

Tags(), Path(), Children(), and FlagNames() all return defensive copies. For callers that only range over the result, an iterator-based API (Go 1.23+ iter.Seq) would eliminate the copy. These are called rarely (help generation, suggestions), so impact is minimal.

6. Email Parsing: 25 Allocations External

ParseEmail uses net/mail.ParseAddress which allocates 25 times (504 B). This is standard library behavior and cannot be improved within cmdguard. Email parsing is rare (once per config field at startup), so this is irrelevant in practice.

  • Primitive parsers are zero-alloc — Duration, LogLevel, Port, HostPort all allocate nothing

  • Spinner auto-skips non-TTY — no goroutine, no writes when piped/redirected
