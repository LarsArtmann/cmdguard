Composability

cmdguard exhibits a well-layered architecture with clear separation between foundation types, registries, flag system, CLI core, and feature extensions. The single-package design (all in v2) keeps coupling manageable for a library of this size. The main architectural concerns are: (1) CLI[T] acts as a god-struct with 17 fields spanning 6 concerns, (2) the type handler system erases generics to any at the internal boundary, losing compile-time safety, and (3) global mutable singletons (globalTypeRegistry, globalValidators, regexCache) limit test isolation.

Coupling Hotspots

🔴 CLI[T] — God Struct

CLI[T] in cli.go has 17 fields spanning 6 distinct concerns:

CLI Identity: name, version, long, rootCmd
Config: cfg, flagRegistry, configPath
DI: scope
Middleware: middlewares
Features: outputFormat, glamourHelp, configFileLoader
Runtime: flowCtx, validationMode, envPrefix

Fan-out: depends on 10+ internal files directly. Every feature addition requires modifying CLI[T].

High Coupling

🟡 cli_command.go — Deep Wiring

Orchestrates Command + FlagRegistry + Middleware + Prompts + clone/parse in a single cliToCobraCommand() function. 218 lines doing 5 distinct jobs.

Moderate Coupling

🟡 Global Singletons

Three mutable package-level registries: globalTypeRegistry, globalValidators, regexCache. Each CLI instance clones from the globals, but the clone-once pattern means updates to globals don't propagate to existing instances.

Test Isolation Risk

Service Orientation Assessment

Current State

The codebase is a well-structured library with clear extension points via functional options and the type handler registry. It is NOT service-oriented in the microservice sense — nor should it be. It's a CLI framework library. The appropriate SOA question is: can consumers compose cmdguard features independently?

Aspect Score Notes
Feature composability Strong Functional options allow independent feature selection. WithMiddleware, WithOutputFormat, WithGlamourHelp etc. are orthogonal.
Type extensibility Strong TypeHandler registry allows adding custom types without modifying the core. Enum/Port/Email etc. are all registered this way.
DI composability Strong samber/do/v2 scope with Provide/Invoke/Shutdown. Child scopes for subcommand isolation. Health checks built-in.
Middleware composability Moderate Chain works well, but middleware only receives config, not command-specific flags. Limits per-command behavior.
Output composability Strong 12 output formats via go-output. Custom format registration possible.
Test composability Moderate testutil package provides TestCLI wrapper. But global singletons make parallel testing of different configs fragile.

Recommendations

1. Split CLI[T] into focused components

Strong

Extract concerns from CLI[T] into focused structs: CLIConfig, CLIFeatures, CLIRuntime. Keep CLI[T] as a facade that delegates. This reduces the fan-out from 10+ to ~3 per component.

Impact: Medium | Effort: High | Priority: Long-term

2. Eliminate global mutable singletons

Strong

Replace globalTypeRegistry, globalValidators, regexCache with instance-scoped registries initialized in NewCLI. Use a RegistryDefaults struct that can be shared explicitly rather than implicitly.

Impact: High (test isolation) | Effort: Medium | Priority: Near-term

3. Bridge the any gap in TypeHandler

Strong

Add runtime type guards at the TypeHandler boundary: verify Parse() return type matches the target field type before setting. This catches tag typos at registration time instead of runtime panics.

Impact: High (type safety) | Effort: Low | Priority: Immediate

4. Unify field-value-to-string conversion

Worth Exploring

Merge fieldValueToString (config_file.go) and formatFieldValue (flags_validate.go) into a single canonical implementation in flag_helpers.go.

Impact: Low (DRY) | Effort: Low | Priority: Quick win

5. Add typed flag access to middleware

Worth Exploring

Middleware currently receives only *T (config) but not command-specific flags. Add a FlagAccessor to CommandInfo so middleware can inspect flags per-command.

Impact: Medium | Effort: Medium | Priority: Medium-term
