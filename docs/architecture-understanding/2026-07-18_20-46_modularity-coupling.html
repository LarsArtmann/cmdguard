Verdict: architecture is at target — do not re-split or merge

The 6-module structure follows the Unix philosophy: each module does one thing, composes via thin interfaces (Middleware[T], PromptRunner, WithHelpTransform[T]), and can be imported independently. A consumer who wants only the core CLI pays for 13 direct deps; one who wants spinner middleware imports the spinner sub-module and pays only for lipgloss. GOWORK=off go build ./... passes per-module, confirming no workspace-only coupling. No changes recommended.

02Coupling Analysis

Sub-modules → core (all one-way, all via interface)

Every sub-module imports github.com/larsartmann/cmdguard/v3/pkg/cmdguard/v3 and attaches via a hook the core exposes:

  • glamour → WithHelpTransform[T](fn) hook
  • prompts → PromptRunner interface + SetPromptRunner()
  • spinner / telemetry → Middleware[T] hook
  • manpage → consumes *cobra.Command via cli.Command(ctx)

Core has zero imports of any sub-module. The dependency graph is a strict DAG. No circular deps. No workspace-only resolution (GOWORK=off go build ./... passes per-module with GOEXPERIMENT=jsonv2).

core v3 ├── glamour (via WithHelpTransform hook) ├── prompts (via PromptRunner interface) ├── spinner (via Middleware[T] hook) ├── telemetry (via Middleware[T] hook) └── manpage (via *cobra.Command consumer) core → cobra, pflag, samber/do, fang, go-output, auditlog, koanf (13 direct)

05Module Proposal (review-only)

Proposed structure: identical to current structure

Per go-modularize Direction Neutrality: both “should we split?” and “should we merge?” answered NO.

  • No split deeper: each sub-module already “does one thing” at the right depth. A 1-2 file module split would create micro-modules with no composability payoff (FM#8 anti-signal).
  • No merge: some consumers import core without prompts/spinner/telemetry/etc. — the seam earns its keep (go-modularize “When NOT to Consolidate” #1).
  • No internal/ extraction: the v3 package is the surface; internals are unexported types, not a separate package.

06Recommendations

1

Do nothing (default)

The module structure is at target. This proposal exists to document the audit, not to drive change.

2

Optional: koanf extraction (only if consumers ask)

koanf/v2 + 3 sub-packages are direct core deps for YAML/TOML config loading. ROADMAP already notes this as a candidate for a configload sub-module. Defer until a consumer explicitly asks for “core without koanf”. Until then, 4 deps is acceptable.

3

Optional: add CI job for GOWORK=off build per module

Catches FM#4 (go.work/replace drift) and FM#12 (workspace-only testing) at PR time. Currently verified manually. A 10-line CI job iterating the 6 modules with GOEXPERIMENT=jsonv2 GOWORK=off go build ./... would lock this in.
