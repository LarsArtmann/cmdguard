Headline: this is what “make invalid states unrepresentable” looks like

The data model is the project's strongest asset. Every domain concept that could be stringly-typed (Email, Port, URL, FilePath, HostPort, Duration, Enum) is a branded struct with a single unexported field and a Parse* constructor that validates at creation time. There is no way to produce an Email value that fails mail.ParseAddress. There is no way to produce a Port outside 1–65535. The Enum type is a closed union: ParseEnum("x", allowed) rejects values outside allowed at the type boundary.

02Problem Catalog (brutal honesty)

P1 Stringly-typed everything — NOT PRESENT

Every domain concept is a branded type. The only raw string fields in domain types are Config.ConfigFile (path to a file, where FilePath would be heavier than needed) and FlagTag fields (which are configuration metadata, not domain concepts). Verdict: clean.

P2 Pointer fields as state encoding — NOT PRESENT

No *time.Time-as-“not yet” pattern. Optional state is handled via zero-value checks (IsEmpty() methods on branded types) or via the localKeys map[any]struct{} set in BranchingFlowContext. No nullable-as-tri-state.

P3 No validation at type level — NOT PRESENT

Every branded type enforces its invariant in its Parse* constructor. Port{} (zero value) is the only “unset” state, and Port.IsValid() distinguishes it. Email{} is empty and Email.IsEmpty() checks it. Construct-valid-or-error is the universal pattern.

P4 Primitive obsession — NOT PRESENT

The 7 branded types are the textbook counter-example to primitive obsession. HostPort even composes Port rather than re-declaring a uint16.

Low

P5 Interface-based unions — Enum uses struct+slice instead

pkg/cmdguard/v3/types_enum.go:11

Enum is a struct with value string + allowed []string. The Go-idiomatic alternative is a sealed interface: type Enum interface { isEnum() } with unexported implementations, or typed constants via iota. The current design is deliberate: it allows runtime-defined enum sets (the allowed list comes from the caller), which a compile-time iota enum cannot do. This is the right call for a CLI library where enum values come from struct tags.

Verdict: accept The runtime-flexibility requirement justifies the struct shape. Document the decision so future readers do not “fix” it.

P6 No composition, only embedding — NOT PRESENT

LogLevel and LogFormat are typed aliases over Enum (type LogLevel Enum), which is composition. HostPort embeds Port as a field (not a promoted method set, but a HAS-A relationship). No deep embedding hierarchies anywhere.

Low

P7 Implicit relationships — FlagTag.Type is reflect.Type

pkg/cmdguard/v3/config.go:28

FlagTag.Type reflect.Type links a flag to its Go type via reflection rather than via a typed identifier. This is inherent to the struct-tag-driven design: the library reads the config struct via reflect, so the type link is necessarily reflect.Type. A branded FlagTypeID would add a layer without removing the reflection. Accept.

Low

P8 No versioning or lifecycle — Config has no CreatedAt/UpdatedAt

pkg/cmdguard/v3/config.go:12

Config is a static configuration record, not a domain entity. It does not need lifecycle fields. The DI Scope has lifecycle hooks (do.HealthcheckerWithContext, do.ShutdownerWithError) via samber/do, so services DO have lifecycle — just not via struct fields. Accept.

P9 Duplicated logic across types — NOT PRESENT

The textMarshal/textUnmarshal generic helpers centralize MarshalText/UnmarshalText for all branded types. requireNonEmpty centralizes the empty-string guard. No validation logic is copy-pasted across Email/Port/URL/etc.

P10–P12 Weak collections / no generics / missing error models — NOT PRESENT

CLI[T] and Command[T,F] are generics. MergeConfigs[T any], Override[T], OverrideValue[T], CloneScope all use generics. Errors are structured (EnumError, CommandError, ConfigError) with errors.Is-chainable sentinels (58 of them).

03The Vision

The model is already at the target state

For a CLI library, the data model cannot be improved materially without breaking the struct-tag-driven API that is the project's core value proposition. The branded types already enforce invariants at construction. The Enum union is deliberately runtime-flexible. The generics are at the right level (Config on CLI, Config+Flags on Command). Forcing more patterns here would be a Verschlimmbesserung.

What “perfect” would look like (and why we are already there)

// Branded type: invalid state unrepresentable
type Email struct{ address string }

// Constructor: validate-or-error
func ParseEmail(s string) (Email, error) {
    addr, err := mail.ParseAddress(s)
    if err != nil { return Email{}, err }
    return Email{address: addr.Address}, nil
}

// Composed type: reuses Port's validation
type HostPort struct{
    host string
    port Port  // branded type composed, not re-declared
}

04Strengths to Preserve

+
Branded primitives with unexported fields The only way to construct an Email is via ParseEmail, which validates. Zero-value is “unset” and IsEmpty() checks it. Textbook “make invalid states unrepresentable”.
+
Generics at the right level CLI[T] parameterizes on Config. Command[T,F] on Config+Flags. Options are non-generic (func(*spec)). This is the v3 design that eliminated the v2 “7 type params per command” explosion.
+
Composition over inheritance HostPort HAS-A Port. LogLevel/LogFormat are typed aliases over Enum. No base structs, no deep embedding.
+
Centralized helpers kill duplication textMarshal[T]/textUnmarshal[T] generic helpers mean each branded type's MarshalText/UnmarshalText is one line. No copy-pasted serialization.
+
Structured errors with sentinel chain 58 sentinels (ErrInvalidEmail, ErrValueOutOfRange, etc.) all chainable via errors.Is. Callers can branch on the exact failure mode.

06Migration Roadmap

Recommendation: do nothing The data model is already at the target state. The three Low findings (P5 Enum shape, P7 FlagTag.Type, P8 Config lifecycle) are all deliberate design choices documented above. Forcing changes would break the struct-tag-driven API or the runtime-flexibility promise.
1

Document the Enum design decision

Add a one-paragraph note to types_enum.go explaining why Enum is a struct (runtime-flexible allowed list) rather than an iota enum or sealed interface. This stops future “why isn't this iota?” questions.

2

Consider ConfigFile FilePath (optional, low priority)

Config.ConfigFile string could become ConfigFile FilePath to brand it. Tradeoff: FilePath validation is heavier than the field needs (it may point to a not-yet-existing file for write paths). Probably not worth it; flag for future review only if ConfigFile misuse becomes a support burden.
